# GitHub Review

Establish what works, what remains and which actions need the user. Report through the identified coordinator when present; otherwise use the current user chat.

## Establish the review

Recover the outcome, acceptance conditions, quality standard and delivery state from the current request or assignment, repository README, owning issues and recorded decisions. Do not depend on an earlier session's unrecorded agreements. Surface an essential missing decision while continuing independent review. Carry existing permissions into the review; invocation does not authorize additional writes, commitments, releases, paid calls or schedules.

Use the [execution relationship and checkout rules in GitHub Execute](github-execute.md) to establish the owner, reporting route and candidate. Do not presume a CTO exists or search unrelated chats to find one. Review delegated source at its assigned boundary; the execution owner remains responsible for integration.

Identify the actual candidate: checkout, branch/commit, relevant uncommitted changes and installed build when applicable; these may differ. Check for active verification, leave its conditions pending and continue independent inspection without duplicating checks or competing for resources.

## Reconcile acceptance evidence

Map each acceptance condition to evidence, a demonstrated defect or a remaining check. Keep the working map in context or the existing review record; do not create another plan, board or tracking issue by default.

- Inspect the implementation and affected flows against the agreed requirements. A passing build alone does not prove behavior.
- Reuse evidence that covers the current behavior and source. Run missing checks, or recheck affected conditions after relevant changes, using proportionate repository verification and isolated test data. Coordinate shared resources with the execution owner.
- Use a fresh, bounded reviewer when independent inspection adds meaningful confidence and delegation is available and authorized. Supply the agreed behavior, source, evidence, reporting route and permitted checks. Routine review does not create a separate sidebar chat.
- Judge against the agreed project quality standard, including required layout or taste review and basic usability. Use your expertise to identify problems without introducing new acceptance requirements.
- Separate defects, missing evidence, physical checks and human judgment. Qualify each pass by the behavior and conditions verified; a checked review item is not necessarily complete issue acceptance. Synthetic inputs do not establish real hardware or recording performance.

Treat recorded decisions as the baseline. Resolve technical details yourself; raise new evidence when it materially changes the intended outcome or a protected commitment. Explain its user effect, recommendation and affected work, and continue independent work while the answer is pending.

## Resolve technical findings

Return actionable defects with their affected requirement, source and evidence to the identified execution owner. Within an assignment that authorizes correction, use GitHub Execute, integrate as required and return to this review to recheck affected evidence. The correction is part of the active review, not another final handoff review. In a review-only assignment, report the finding rather than starting implementation.

Preserve active writers' work and coordinate corrections that would change their candidate. If a technical blocker prevents progress, name the unfinished condition and resumable source. Do not repeat unchanged failing checks without corrective action or new evidence, or turn routine technical failures into user approval requests.

## Prepare the remaining handoff

When GitHub updates are authorized, perform review bookkeeping without another routine approval request:

- Use the repository's established review conventions and confirmed reviewer, rather than assuming the repository owner is the assignee. Set labels and assignments to reflect remaining human work, preserving unresolved human-review requests even when tests pass.
- Maintain one concise review summary/checklist on an existing owning issue, linking affected issues for a batch. Reuse the existing review comment where authorized and preserve others' edits. Link detailed technical evidence in its existing location. Use a filtered GitHub URL when a review view is useful.
- Explain what changed in user terms, what automated review established, which candidate/build it covers and where to review. The remaining human checklist contains only decisions, required human judgments, essential inputs or physical checks agents cannot settle. Distinguish an installed build from one awaiting installation.

Perform authorized bookkeeping using confirmed metadata; report unavailable parts through the current chat or coordinator route. Do not substitute another persistent record or claim a write succeeded. Merge, release and closure still require their agreed delivery conditions and authorization.

Return the reviewed candidate/issues, demonstrated failures or external blockers, and remaining human actions with concise evidence references. If no human action remains, say so. The execution owner can continue its approved work without a routine sign-off; review does not authorize a new scope.
